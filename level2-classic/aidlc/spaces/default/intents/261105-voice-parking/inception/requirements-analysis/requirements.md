## 의도 분석

사용자는 자연어 한 문장으로 "어디서, 얼마나 오래" 주차할지 말하고, 시스템이 조건에 맞는 주차권 중 최적 1개와 비교 후보 2개를 이유와 함께 제안해 주기를 원한다. 사용자가 하나를 골라 결제하면 예약이 확정되고, 확정 사실이 지연 없이 화면에 보이는 것이 핵심 가치다. 목적은 이 전체 흐름이 동작함을 보여 주는 프로토타입이다.

## 기능 요구사항

### FR1. 음성 텍스트 입력 해석
- FR1.1 시스템은 사용자가 보낸 한국어 음성 텍스트에서 장소(예: 강남역)와 이용 시간(예: 2시간)을 추출한다.
- FR1.2 장소 또는 이용 시간을 추출하지 못하면 시스템은 무엇이 부족한지 안내하는 메시지를 돌려주고 추천을 수행하지 않는다.
- FR1.3 음성 인식(STT) 자체는 범위 밖이며 시스템은 이미 텍스트로 변환된 입력만 받는다.

### FR2. 주차권 후보 조회
- FR2.1 시스템은 요청 장소 주변의 목업 주차장·주차권 데이터에서 후보를 찾는다.
- FR2.2 사용 가능 시간이 요청 이용 시간을 포함하지 못하는 주차권은 후보에서 제외한다.
- FR2.3 조건에 맞는 후보가 하나도 없으면 시스템은 "조건에 맞는 주차권이 없음"을 사용자에게 알린다.

### FR3. 종합 점수 추천
- FR3.1 시스템은 후보마다 종합 점수 = 가격 점수 × 0.4 + 거리 점수 × 0.4 + 시간 적합도 점수 × 0.2를 계산한다.
- FR3.2 가격 점수와 거리 점수는 후보 간 min-max로 0~100점으로 환산하며 값이 낮을수록 높은 점수를 준다. 후보가 하나뿐이거나 모든 값이 같으면 해당 항목은 100점이다.
- FR3.3 시간 적합도 점수는 사용 가능 시간이 요청 시간을 포함하고 그 차이가 작을수록 100점에 가깝다.
- FR3.4 시스템은 종합 점수 상위 1개를 최적으로, 다음 2개를 비교 후보로 보여 준다. 후보가 3개 미만이면 있는 만큼만 보여 준다.
- FR3.5 각 추천에는 가격·거리·시간 적합도 중 어느 점이 점수에 기여했는지를 설명하는 추천 이유를 함께 보여 준다.
- FR3.6 종합 점수가 같으면 가격이 낮은 후보를 우선한다. [assumption] 동점 규칙은 사용자 확인이 없는 가정이다.

### FR4. 선택·결제 요청·예약 대기
- FR4.1 사용자는 보여 준 3개 후보 중 하나를 선택해 결제를 요청할 수 있다.
- FR4.2 결제 요청 시 시스템은 모의 PG에 결제를 요청하고 예약을 "결제 대기" 상태로 만든다.
- FR4.3 결제 대기 중에는 화면에 승인 대기 중임을 표시한다.

### FR5. 비동기 웹훅 승인 처리
- FR5.1 모의 PG의 결제 승인은 비동기 웹훅 호출로 시스템에 전달된다.
- FR5.2 승인 웹훅을 받으면 시스템은 해당 예약을 "예약 완료"로 확정한다.
- FR5.3 같은 승인 웹훅이 여러 번 와도 예약은 한 번만 확정된다.
- FR5.4 이미 취소된 예약에 대한 승인 웹훅은 예약을 되살리지 않고 무시하며 그 사실을 기록한다.
- FR5.5 모의 PG는 승인뿐 아니라 승인 지연과 실패 시나리오를 선택해 재현할 수 있다.

### FR6. 예약 완료 즉시 표시
- FR6.1 시스템은 SSE로 예약 상태 변화를 화면에 푸시한다.
- FR6.2 예약이 확정되면 화면은 예약 완료(주차장, 이용 시간, 결제 금액)를 표시한다.
- FR6.3 결제 요청 후 화면은 SSE 연결이 끊겨도 같은 예약의 현재 상태를 다시 받아 올 수 있다.

### FR7. 승인 지연 자동 취소
- FR7.1 결제 요청 시점부터 180초 안에 승인이 없으면 시스템은 예약을 자동 취소한다.
- FR7.2 자동 취소되면 같은 SSE 푸시로 화면에 "승인 지연으로 예약이 취소되었습니다"를 즉시 표시한다.

### FR8. 익명 사용자
- FR8.1 로그인 없이 브라우저 세션 단위로 사용자를 식별하고 그 세션의 예약만 조회할 수 있다.

### FR9. 로컬 데모 실행
- FR9.1 모든 서비스와 프런트는 실행 스크립트로 로컬에서 기동할 수 있다.

## 비기능 요구사항

- NFR1. 승인 웹훅 수신 시각부터 화면에 예약 완료가 표시되기까지 1초 이내여야 한다 (측정: 로컬 환경, 100건 반복에서 최대 1초).
- NFR2. 자동 취소는 결제 요청 시점부터 180초 ± 2초 안에 수행되어야 한다.
- NFR3. 음성 텍스트 입력 후 추천 결과(최적 1개와 후보 2개) 표시까지 2초 이내여야 한다 (로컬 환경 목업 데이터 기준). [assumption]
- NFR4. 프런트는 Vue 3, 백엔드는 Java Spring Boot이며, 백엔드 모듈이 여럿이면 마이크로서비스로 분리한다.
- NFR5. 웹훅 처리는 멱등해야 한다 (같은 승인 이벤트 N회 수신 시 예약 확정은 정확히 1회).
- NFR6. 웹훅 요청은 공유 비밀 값으로 검증하며 비밀 값은 코드에 하드코딩하지 않고 환경 변수로 주입한다.
- NFR7. 개발은 TDD(실패 테스트 먼저)로 하고 라인 커버리지 80% 이상을 유지하며 병합 전 CI에서 실행한다.
- NFR8. Docker와 별도 배포 환경을 사용하지 않고 로컬 실행 스크립트로만 실행한다.
- NFR9. Java는 IDE 기본 설정, Vue는 ESLint와 Prettier를 따른다.

## 제약

- 기술 스택: 프런트 Vue 3, 백엔드 Java Spring Boot, 마이크로서비스 (NFR4).
- 팀 규칙: Docker 금지, 별도 배포 환경 금지, 로컬 실행 스크립트 필수.
- 외부 연동 금지: 실제 지도·주차장 API와 실제 결제대행사 연동은 하지 않는다.

## 가정

- [assumption] 사용자 입력은 한국어 한 문장이며 장소는 지하철역 등 목업 데이터에 등록된 이름으로 한정한다. 근거: 목업 데이터를 쓰는 프로토타입.
- [assumption] 요청 장소와 주차장 사이의 거리는 목업 데이터에 미리 담긴 미터 값 또는 좌표 간 직선거리로 계산한다. 근거: 지도 API 없음.
- [assumption] 마이크로서비스를 몇 개로 나눌지는 이후 설계 단계에서 정한다. 근거: 모듈 경계는 도메인 설계의 산출물이다.
- [assumption] 예약 확정 시 목업 재고(잔여 주차권 수)를 차감하지 않는다. 근거: 사용자가 재고 관리를 요청하지 않았다.

## 범위 밖

- 음성 인식(STT), 로그인과 회원 관리, 실제 PG·지도 연동, 환불과 예약 변경, 운영 배포.

## Assumptions & Open Questions

- 위 가정 4건과 FR3.6 동점 규칙은 사용자 확인 전까지 가정으로 유지한다.
- 열린 질문: 마이크로서비스 경계(추천, 결제, 예약 등 몇 개로 나눌지)는 도메인 설계에서 결정한다.
