## US1.1 음성 텍스트로 장소·시간 말하기

As a 운전자, I want to 음성 텍스트로 "강남역 근처 2시간 주차권 찾아줘"처럼 장소와 시간을 말하고, so that 검색 조건을 직접 입력하지 않고도 주차권을 찾을 수 있다.

- 우선순위: Must Have
- 의존: 없음
- INVEST: 독립적으로 시연 가능(해석 결과만 확인), 작고 테스트 가능하다.

Acceptance criteria:
- AC1.1.1 Given 사용자가 세션을 시작했을 때, When "강남역 근처 2시간 주차권 찾아줘"를 보내면, Then 시스템은 장소를 "강남역", 이용 시간을 2시간으로 해석해 추천 단계로 넘긴다.
- AC1.1.2 Given 장소가 빠진 입력 "2시간 주차권 찾아줘"일 때, When 보내면, Then 장소가 필요하다는 안내가 보이고 추천은 수행되지 않는다.
- AC1.1.3 Given 이용 시간이 빠진 입력 "강남역 근처 주차권 찾아줘"일 때, When 보내면, Then 이용 시간이 필요하다는 안내가 보이고 추천은 수행되지 않는다.
- AC1.1.4 Given 로그인하지 않은 새 브라우저일 때, When 입력을 보내면, Then 브라우저 세션 단위로 사용자가 식별되어 같은 세션의 예약만 조회된다.

## US2.1 조건에 맞는 주차권 후보 보기

As a 운전자, I want to 요청 장소 주변에서 내 이용 시간을 충족하는 주차권만 보고, so that 쓸 수 없는 주차권을 걸러 낼 수 있다.

- 우선순위: Must Have
- 의존: US1.1
- INVEST: 목업 데이터로 독립 검증 가능.

Acceptance criteria:
- AC2.1.1 Given 강남역 주변에 이용 시간 2시간을 포함하는 목업 주차권 5개가 있을 때, When 2시간을 요청하면, Then 5개가 후보로 조회된다.
- AC2.1.2 Given 사용 가능 시간이 1시간뿐인 주차권이 있을 때, When 2시간을 요청하면, Then 그 주차권은 후보에서 제외된다.
- AC2.1.3 Given 조건에 맞는 주차권이 하나도 없을 때, When 요청하면, Then "조건에 맞는 주차권이 없음" 안내가 보인다.

## US2.2 종합 점수로 최적 1개와 비교 후보 2개 추천받기

As a 운전자, I want to 가격 40%, 거리 40%, 이용 시간 적합도 20%로 계산한 종합 점수로 최적 1개와 비교 후보 2개를 이유와 함께 받고, so that 직접 비교하지 않고도 빠르게 고를 수 있다.

- 우선순위: Must Have
- 의존: US2.1
- INVEST: 점수 계산을 숫자 예시로 검증하므로 테스트 가능하다.

Acceptance criteria:
- AC2.2.1 Given 후보 3개의 가격 점수가 100·50·0, 거리 점수가 80·100·0, 시간 적합도 점수가 100·60·0일 때, When 추천하면, Then 종합 점수는 각각 92·72·0이고 순서는 첫째, 둘째, 셋째가 된다. (92 = 100×0.4 + 80×0.4 + 100×0.2, 72 = 50×0.4 + 100×0.4 + 60×0.2)
- AC2.2.2 Given 후보가 5개일 때, When 추천하면, Then 종합 점수 상위 1개는 "최적", 다음 2개는 "비교 후보"로 총 3개가 보이고 나머지는 보이지 않는다.
- AC2.2.3 Given 후보가 2개뿐일 때, When 추천하면, Then 있는 2개만 보인다.
- AC2.2.4 Given 종합 점수가 같은 후보 두 개가 있을 때, When 추천하면, Then 가격이 낮은 후보가 앞선다.
- AC2.2.5 Given 최적 후보의 가격 점수가 가장 큰 기여 항목일 때, When 추천 이유를 보면, Then 이유에 "가격" 항목이 가장 큰 기여로 표시된다.
- AC2.2.6 Given 음성 텍스트를 보낸 시각을 기준으로, When 목업 데이터로 추천하면, Then 추천 결과 표시까지 2초 이내이다. [assumption] 요구사항 NFR3의 목표는 사용자 확인 전 가정이다.

## US3.1 후보를 골라 결제 요청하기

As a 운전자, I want to 추천된 3개 후보 중 하나를 골라 결제를 요청하고, so that 마음에 드는 주차권을 확보할 수 있다.

- 우선순위: Must Have
- 의존: US2.2
- INVEST: 모의 PG를 사용해 독립 검증 가능.

Acceptance criteria:
- AC3.1.1 Given 추천 목록이 보일 때, When 후보 하나를 골라 결제를 요청하면, Then 예약이 "결제 대기" 상태로 만들어지고 모의 PG에 결제가 요청된다.
- AC3.1.2 Given 예약이 결제 대기일 때, When 화면을 보면, Then 승인 대기 중임이 표시된다.
- AC3.1.3 Given 이미 결제 대기 중인 예약이 있을 때, When 같은 세션에서 다시 결제를 요청하면, Then 새 결제는 만들어지지 않고 기존 예약의 대기 상태가 계속 보인다. [assumption] 세션당 동시 결제 대기 1건으로 제한한다는 가정이다.

## US3.2 결제 실패 후 다른 후보로 다시 결제하기

As a 운전자, I want to 결제가 거절되면 실패 안내를 보고 같은 목록의 다른 후보로 다시 결제하고, so that 처음부터 다시 말하지 않고 예약을 이어 갈 수 있다.

- 우선순위: Should Have
- 의존: US3.1
- 출처: [Q3] (요구사항 FR5.5에서 확장). 요구사항 검토에서 결제 실패 후 동작이 빠졌다는 지적을 이 스토리에서 닫는다.

Acceptance criteria:
- AC3.2.1 Given 모의 PG가 결제 실패(거절) 시나리오일 때, When 거절 웹훅이 오면, Then 예약은 "결제 실패" 상태가 되고 화면에 실패 안내가 보인다.
- AC3.2.2 Given 결제 실패 안내가 보일 때, When 같은 추천 목록에서 다른 후보를 골라 결제하면, Then 새 예약이 결제 대기 상태로 만들어진다.
- AC3.2.3 Given 결제 실패로 끝난 예약이 있을 때, When 시간이 지나도, Then 실패한 예약은 "예약 완료"로 바뀌지 않는다.

## US4.1 결제 승인 직후 예약 완료 보기

As a 운전자, I want to 결제가 승인되면 곧바로 화면에서 예약 완료를 보고, so that 예약이 확정됐다고 안심할 수 있다.

- 우선순위: Must Have
- 의존: US3.1
- INVEST: 웹훅 수신 시각과 화면 표시 시각을 측정해 검증한다.

Acceptance criteria:
- AC4.1.1 Given 예약이 결제 대기이고 화면이 서버 푸시(SSE)로 연결돼 있을 때, When 모의 PG의 승인 웹훅이 오면, Then 웹훅 수신 시각부터 1초 이내에 화면에 예약 완료(주차장, 이용 시간, 결제 금액)가 표시된다.
- AC4.1.2 Given 같은 승인 웹훅이 3번 도착해도, When 처리하면, Then 예약 확정은 정확히 1회이다.
- AC4.1.3 Given 올바르지 않은 비밀 값이 붙은 웹훅이 올 때, When 처리하면, Then 요청은 거부되고 예약 상태는 바뀌지 않으며 그 사실이 기록된다. [assumption] 요구사항 검토 지적(R-04)을 닫는 가정이다.
- AC4.1.4 Given 푸시 연결이 끊겼을 때, When 화면이 다시 연결하면, Then 같은 예약의 현재 상태(예약 완료 포함)를 다시 받아 볼 수 있다.
- AC4.1.5 Given 이미 자동 취소된 예약에 승인 웹훅이 늦게 오면, When 처리하면, Then 예약은 되살아나지 않고 무시된 사실이 기록된다.

## US4.2 승인 지연 시 예약 자동 취소 안내받기

As a 운전자, I want to 승인이 오래 안 오면 예약이 자동 취소되고 그 사실을 바로 알려 받고, so that 결제 대기 상태로 오래 묶이지 않는다.

- 우선순위: Must Have
- 의존: US3.1
- INVEST: 시간 제어가 가능한 테스트 시계로 검증한다.

Acceptance criteria:
- AC4.2.1 Given 결제 요청 시점부터 승인이 오지 않을 때, When 180초가 지나면, Then 예약이 자동 취소되고 화면에 "승인 지연으로 예약이 취소되었습니다"가 즉시 표시된다.
- AC4.2.2 Given 결제 요청 후 179초에 승인 웹훅이 올 때, When 처리하면, Then 예약은 완료되고 자동 취소는 일어나지 않는다.
- AC4.2.3 Given 결제 요청 후 181초에 승인 웹훅이 올 때, When 처리하면, Then 예약은 이미 취소 상태이며 되살아나지 않는다. [assumption] 180초 경계 규칙: 취소가 먼저 확정되면 이후 승인은 무시한다.
- AC4.2.4 Given 자동 취소 타이머가 동작할 때, When 취소 시각을 측정하면, Then 결제 요청 시점부터 180초 ± 2초 안이다.

## US5.1 로컬에서 한 번에 실행해 데모하기

As a 운전자(데모를 보는 사용자), I want to 로컬에서 실행 스크립트 한 번으로 전체 서비스를 띄워 데모를 보고, so that 별도 배포 환경 없이 전체 흐름을 확인할 수 있다.

- 우선순위: Must Have
- 의존: US1.1~US4.2
- INVEST: 실행 스크립트로 전체 흐름을 한 번에 검증한다.

Acceptance criteria:
- AC5.1.1 Given Docker 없이 로컬 환경일 때, When 실행 스크립트를 한 번 실행하면, Then 화면과 모든 백엔드 서비스가 기동된다.
- AC5.1.2 Given 모든 서비스가 기동되어 있을 때, When "강남역 근처 2시간 주차권 찾아줘"로 시작해 승인 시나리오까지 진행하면, Then 예약 완료 화면까지 도달한다.
- AC5.1.3 Given 실행 스크립트가 실패한 서비스가 있을 때, When 실행하면, Then 어느 서비스가 기동하지 못했는지 오류 메시지로 알려 준다.
