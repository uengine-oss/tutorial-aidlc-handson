## 설계

| 설계 | 방식 | 충족하는 요구사항 |
|---|---|---|
| 즉시 반영 | 구독 이벤트 처리기는 스냅샷을 검사(예약별 version 필터)한 뒤 같은 동기 호출 안에서 반응형 상태를 바꾼다. 디바운스, 애니메이션 지연, `setTimeout` 대기를 두지 않는다. Vue는 상태 변경 뒤 다음 마이크로태스크에서 DOM을 갱신한다. | NFR1.1 |
| 얇은 처리 | 이벤트당 일은 JSON 해석, 형식 확인, 상태 갱신, aria-live 문구 교체뿐이다. 카드 목록은 최대 3개라 가상 목록이나 메모이제이션이 필요 없다. | NFR1.1, NFR3.1 |
| 프록시는 통과만 | SSE 경로(`/api/reservations/**`)의 프록시는 응답을 변환하지 않고 그대로 흘린다(`changeOrigin` 외 변환 없음). 이벤트 스트림이 압축으로 모이는 위험(업스트림이 `Accept-Encoding`을 받아 압축하는 경우)은 프록시 요청의 `Accept-Encoding`을 `identity`로 고정해 막고, L2에서 응답에 `Content-Encoding`이 없음을 확인한다. 프록시 `timeout`과 `proxyTimeout`은 같은 값 600000ms(10분, 예약 자동 취소 180초보다 충분히 길다)로 정하고, `vite.proxy.js`의 내보낸 설정값이 이 값임을 단위 시험으로 확인한다. | NFR1.2 |
| 요청 제한 시간 | `api` 모듈이 `AbortController`로 요청마다 3초 제한을 건다. 이 3초는 서비스 호출 제한 시간 2초(계약 표) 뒤에 1초 여유를 둔 값이다. 추천의 2초 목표(NFR3)는 u1이 서비스 쪽에서 측정하는 값이며 화면은 2초를 강제하지 않는다. 화면은 응답이 오는 즉시 보이고, 3초를 넘기면 실패로 다룬다. | NFR3.2 |
| 틱 | 경과 시간 틱은 `useApp`의 하나의 `setInterval(1000)`이 갱신하고 예약 상태 영역만 다시 그린다(계산 값 `elapsedSeconds` 하나). 결제 대기가 끝나면 즉시 해제한다. | NFR1.3 |
| 복구 | 구독 복구는 1초, 2초, 5초, 5초… 물러나기로 총 60초 안에서만 시도하며 한 번에 하나의 복구 타이머만 둔다. 구독 교체 때는 기존 구독을 먼저 닫고, 탭이 닫히거나 새로 고쳐질 때(`pagehide`)도 구독을 닫는다. | NFR1.4 |
| 브라우저 연결 한도 | 개발 서버는 HTTP/1.1이라 같은 오리진에 동시 연결이 6개로 제한된다. SSE 구독이 하나를 차지하므로 대기 중 탭을 여러 개 열면 다른 탭의 일반 요청이 3초 제한 시간에 걸릴 수 있다. 이 한계를 받아들이고 시연 절차에 "결제 대기 중 탭은 하나"를 적는다(u5·시연 안내). 서버 쪽 구독 상한 32(503 SUBSCRIPTION_LIMIT)와는 무관하며 그 오류는 복구 규칙으로 닫는다. | NFR3.2 |

## 시험 계층과 한계 (검토에서 넘어온 항목)

시간 시험은 세 계층이며 각 계층이 무엇을 증명하고 무엇을 증명하지 못하는지 분명히 한다.

| 계층 | 도구 | 증명하는 것 | 증명하지 못하는 것 |
|---|---|---|---|
| L1 단위 | Vitest + jsdom, 가짜 `EventSource`·`fetch` | 앱 코드가 이벤트를 받은 즉시 상태를 바꾸고 DOM에 반영하는 것(NFR1.1, NFR3.1, NFR1.3). 이 계층의 100ms는 "화면 코드가 지연을 만들지 않는다"는 회귀 가드이지 실제 브라우저 렌더링 시간이 아니다 | 실제 브라우저의 `EventSource` 자동 재연결, 실제 렌더링·페인트 시간 |
| L2 프록시 통합 | Vitest(Node 환경) + 실제 Vite `createServer`가 `vite.proxy.js`를 읽어 기동, 시험용 SSE 서버·시험용 u3 서버를 뒤에 둠, 수신 클라이언트는 Node `http.get` | 실제 Vite의 프록시 키 해석·`bypass`가 웹훅 경로를 막는 것, SSE 이벤트가 버퍼링 없이 전달되는 것(NFR1.2, NFR6.3) | 브라우저 쪽 동작 |
| L3 브라우저 | Build and Test의 수동 확인 절차(아래) | 실제 브라우저에서 이벤트가 오면 화면이 바뀌고 연결이 끊겼다 다시 이어지는 것 | 반복 통계(수동이라 몇 회 관찰) |

### L3 브라우저 확인 절차 (책임: Build and Test의 품질 담당, 시연 시 사람이 확인)

1. 세 서비스와 화면을 로컬 스크립트로 띄운다(u5). 브라우저 개발자 도구의 Network에서 `/api/reservations/*/events`가 `text/event-stream`으로 열린 것을 확인한다.
2. 시연 설정 승인으로 결제하고, 결제 대기에서 예약 완료로 바뀌는 시각을 서비스 로그의 푸시 시각과 비교한다. 5회 반복해 모두 1초 안에 바뀌는지 본다.
3. 결제 대기 중 개발자 도구에서 오프라인으로 바꿨다 되돌려 화면이 같은 예약의 현재 상태를 다시 받아 보이는지 확인한다.
4. 새로 고침 뒤 같은 상태가 복원되는지 확인한다.

이 절차는 반복 통계를 대신하지 않는다. 실제 브라우저의 반복 측정(Playwright 등)은 이번 프로토타입 범위에서 도입하지 않으며, 필요하면 후속 변경으로 다룬다.

### 판정 통계 (NFR1.1~NFR1.4, NFR3.1의 시험 규칙)

구간별 시험은 단위 가드이며 NFR1의 "100건 반복에서 최대 1초" 판정을 대신하지 않는다. 최종 판정은 Build and Test의 합산 측정이 상위 요구사항의 최댓값 기준으로 한다.

- 예열 20회 버림, 이어서 100회(L2는 120이벤트 중 앞 20개 버리고 뒤 100개)를 잰다. 출력에 중앙값, p99, 최댓값을 남긴다.
- 합격: p99가 한도 이하이고 최댓값이 한도의 2배 이하다. 재실행으로 가리지 않는다. (기능 요구사항에서 3배로 적은 최댓값 상한을 이 설계가 2배로 좁힌다.)
- 구간 한도의 합이 1초 예산 안에 드는지 확인한다: 이 유닛의 화면·프록시 몫은 최댓값 상한(각 100ms 한도 × 2 = 200ms씩, 합 400ms)이고, u3 웹훅 처리 150ms와 u2 반영·푸시 150ms는 각 서비스가 자기 요구사항으로 정한 한도(합 300ms)다. 합계 700ms ≤ 1000ms다. 두 서비스에 같은 2배 규칙을 적용하면 합이 1000ms로 여유가 없으므로, 합산 검증은 다른 유닛의 최댓값 규칙이 아니라 Build and Test의 실측이 한다.
- L2의 프록시 시험은 같은 이벤트를 직접 수신(프록시 없이)과 프록시 경유로 받아 이벤트별 지연 차이로 판정한다. 이벤트 120개(50ms 간격) 중 앞 20개를 예열로 버리고 100개의 p99 ≤ 100ms, 최댓값 ≤ 200ms이다. 요구사항의 "20개, 250ms 간격"을 표본 수를 늘려 p99가 의미를 갖도록 100개 판정으로 바꾼 것이다. 묶임 판정: 인접한 두 이벤트의 수신 시각 간격이 보낸 간격(50ms)의 절반(25ms) 미만이면 한꺼번에 도착한 것으로 보며 한 건이라도 있으면 실패다. 이벤트 개수는 직접 수신과 같아야 한다.
- 틱(NFR1.3)은 가장 지터에 민감하므로 p99 ≤ 5ms, 최댓값 ≤ 20ms(4배)로 하며 이 값을 NFR1.3의 판정 규칙으로 쓴다.
- 시간 민감 시험은 별도 Vitest 프로젝트(`timing`)로 분리해 순차 실행한다(`fileParallelism: false`, 단일 워커). 파일 이름은 `*.timing.test.js`다. 환경은 프로젝트별 `environment`로 정한다: `unit`과 `timing`의 L1은 jsdom, `proxy`(L2)는 node. 시간 한도는 계측이 없는 `test` 실행에서 판정한다. `test:coverage`는 `unit` 프로젝트만 계측하고 시간 시험을 돌리지 않아(계측으로 느려진 상태에서 시간을 재지 않는다), 커버리지 하한은 `unit` 시험으로 맞춘다.

## 만든 스크립트 정의 (npm)

| 스크립트 | 내용 |
|---|---|
| `dev` | Vite 개발 서버(루프백, 포트 5173 고정 `strictPort: true`, 이미 쓰는 중이면 실패) |
| `test` | `vitest run` (프로젝트 `unit`, `timing`, `proxy` 모두; 시간 한도 판정) |
| `test:coverage` | `vitest run --project unit --coverage` (라인 80% 하한 임계값, 시간 시험 제외) |
| `lint` | ESLint + Prettier 검사 |
| `build` | `vite build` (컴파일 확인용, 배포하지 않음) |
| `audit:report` | `npm audit --audit-level=high`를 실행해 보고서를 출력하고 종료 코드는 0(보고 전용). 레지스트리에 닿지 못하면 "audit 불가"를 출력한다 |
| `verify` | `lint` → `test` → `test:coverage` → `build` → `audit:report` 순서로 실행. audit:report를 뺀 앞의 네 단계 중 하나라도 실패하면 실패 (NFR7.1, NFR6.7). 마지막 단계의 출력이 병합 전 검증 기록에 남는다 |

커버리지 범위(`coverage.include`)는 `src/**`와 `vite.proxy.js`이며 제외는 부트스트랩 `src/main.js`와 시험 파일뿐이다. 이 외의 제외로 하한을 우회하지 않는다.

## Assumptions & Open Questions

- [assumption] L3(실제 브라우저) 확인은 반복 통계 없이 수동 절차로 한다. 근거: 이번 프로토타입은 브라우저 E2E 도구를 두지 않기로 했고(tech-stack-decisions.md 대안), 실제 브라우저의 `EventSource` 동작은 jsdom이 흉내 낼 수 없다. 책임은 Build and Test의 품질 담당이다.
- 열린 질문: 없음.
