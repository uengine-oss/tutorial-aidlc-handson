## 푸시 경로 모델

상태를 확정하는 일(잠금 안)과 연결에 쓰는 일(잠금 밖)을 나누고, 둘 사이의 순서는 연결별 큐로 잇는다.

1. **잠금 안 (예약 단위 잠금)**: 상태 판정과 변경, 스냅샷 만들기, Notification의 `publish` 호출. `publish`는 입출력 없이 (a) 최신 스냅샷을 version 규칙(BR4.2)으로 갱신하고 (b) 그 예약의 구독 목록을 훑어 각 연결의 큐 끝에 스냅샷을 넣기만 한다. 같은 예약의 큐 삽입 순서는 잠금 순서이므로 version 순서와 같다.
2. **잠금 밖 (연결별 쓰기)**: 연결마다 FIFO 큐와 "배출 중" 표시가 하나씩 있다. 큐가 비어 있지 않고 배출 중이 아니면 푸시 실행기에 배출 작업 하나를 낸다. 배출 작업은 큐 앞에서부터 `SseEmitter.send`를 순서대로 부른다. 한 연결에는 동시에 배출 작업이 하나뿐이라 쓰기가 겹치지 않고 순서가 뒤집히지 않는다.
3. **연결 유지 신호**도 같은 연결 큐에 넣는다(주석 항목). 그래서 이벤트 쓰기와 연결 유지 쓰기가 한 연결에서 겹치지 않는다. 주기 실행은 감시 스케줄러(스레드 1개)가 맡는다.
4. **구독 시작**: 예약 단위 잠금 안에서 (a) 구독을 목록에 등록하고 (b) 그 시점의 최신 스냅샷을 새 연결 큐의 첫 항목으로 넣는다. 쓰기는 잠금 밖에서 일어난다. 등록과 읽기가 같은 잠금 안이므로 이후의 모든 `publish`는 이 연결의 큐에 뒤따라 들어가고, 이전의 `publish`는 이미 최신 스냅샷에 반영되어 있다. 누락도 순서 역전도 없다.
5. **잠금 획득 순서**: 세션 잠금 → 예약 잠금 → Notification 내부 구조 → 연결 큐. 역순으로 획득하지 않는다. Notification과 연결 큐는 입출력과 콜백이 없는 잎 구조라 다른 잠금을 더 잡지 않는다.

| 설계 | 방식 | 충족하는 요구사항 |
|---|---|---|
| 메모리 안 처리 | 예약, 판정 기록, 최신 스냅샷은 프로세스 메모리의 맵에 둔다. 결과 반영 경로에는 외부 입출력이 없다(u1 호출은 예약 생성 경로에만 있다). | NFR1.1, NFR1.2 |
| 짧은 임계 구역 | 잠금 안에서는 판정, 상태 변경, 판정 기록 저장, 큐 삽입만 한다. 스냅샷 JSON 직렬화는 배출 작업에서 하고, 잠금 안에는 불변 스냅샷 객체만 만든다. 연결에 쓰는 일은 모두 잠금 밖이라 느린 클라이언트가 같은 예약의 다음 판정을 막지 않는다. | NFR1.1, NFR2.2 |
| 연결별 쓰기 큐 | 위 2~3. 순서와 직렬성은 연결별 큐가 보장하고, 느린 연결은 자기 큐만 키운다. 큐 길이 상한은 16이며 넘으면 그 연결을 끊는다(화면은 재연결해 최신 스냅샷을 받는다). | NFR1.1, NFR2.2, NFR5.4 |
| 푸시 실행기 | 스레드 수 상한 32, 큐 없는 직접 인계(`SynchronousQueue`). 동시 구독 수 상한도 32이며 33번째 구독은 503 `SUBSCRIPTION_LIMIT`로 거절한다. 구독 수가 스레드 수를 넘지 않고 연결당 배출 작업이 하나뿐이므로, 느린 연결이 스레드를 모두 잡아 다른 연결을 굶길 수 없다. | NFR1.1, NFR2.2, NFR4.2 |
| 취소 타이머 스케줄러 | 스레드 2개. 상태 확정까지만 하고 쓰기는 하지 않는다. 확정 시 `publish`가 큐에 넣고 푸시 실행기가 이어받는다. | NFR2.1, NFR2.2 |
| 느린 쓰기 감시 | 배출 작업은 쓰기 시작 시각을 기록한다. 감시 스케줄러가 1초 넘게 끝나지 않은 쓰기의 연결을 닫는다(`completeWithError`). | NFR5.4 |
| u1 호출 마감 | 전체 마감 1.5초. 시도 하나의 제한은 350ms, 시도 사이 간격은 200ms, 남은 시간이 200ms 미만이면 새 시도를 시작하지 않는다. 시작 시각은 0, 550ms, 1100ms라 최대 3회 호출(계약 C4의 "최대 2회 재시도")이 가능하고 마지막 시도는 남은 시간으로 제한되어 1.5초 안에 끝난다. 호출자 u3의 제한 2초 안에서 502까지 끝난다. | NFR1.4, NFR5.5 |
| 세션 잠금 범위 | u1을 부르는 동안에는 세션 잠금을 쥐지 않는다. 결제 대기 확인은 호출 전에 한 번, 저장 직전에 잠금 안에서 다시 한 번 한다(BR1.3). | NFR1.4, NFR4.2 |
| 시계 기반 마감 | 타이머는 마감 시각에 한 번 울리도록 예약하고, 결과 반영 경로는 시계로 마감을 다시 판정한다. 취소 시각의 오차는 스케줄러 지연에 한정된다. | NFR2.1 |

## 시험 방법

- 측정 구간: 요청 필터 진입부터 연결에 `SseEmitter.send`가 반환될 때까지(NFR1.1), 요청 필터 진입부터 응답 쓰기까지(NFR1.2, NFR1.4), 연결 열기부터 첫 이벤트 쓰기까지(NFR1.3), 취소 확정부터 `send` 반환까지(NFR2.2).
- 반복: 처음 20회는 예열로 버리고 이어지는 100회의 최댓값을 목표와 비교한다. JVM 정지로 흔들리면 같은 시험을 한 번 다시 실행해 두 번 모두 넘으면 실패로 본다.
- **느린 클라이언트 시험**: 읽지 않는 연결 1~4개가 열려 있어도 다른 예약의 승인 푸시와 취소 푸시가 150ms 안에 나가는지 확인한다.
- **순서 시험**: 한 예약에 version 2, 3 푸시를 빠르게 연달아 내고 한 연결에서 version이 단조 증가하는지 확인한다. 구독 등록과 푸시를 동시에 반복해 (a) 첫 이벤트가 등록 시점의 최신 스냅샷이고 (b) 이후 이벤트가 빠짐없이 뒤따르는지 확인한다.
- 180초 실시간 취소 시험은 마감 시간을 설정(`reservation.payment-timeout`, 기본 180초)으로 두어 일상 실행에서는 2초 같은 짧은 값으로 실제 스케줄러 경로를 확인하고, 실제 180초 시험은 `slow`로 표시해 병합 전 검증 실행에만 포함한다. 주입 시계를 쓰는 경계 시험은 대기 없이 실행한다(NFR2.4).

## Assumptions & Open Questions

- [assumption] u1 호출의 전체 마감 1.5초와 시도 제한 350ms는 계약 C4가 정한 2초 제한보다 짧다. 호출하는 쪽이 더 짧은 제한을 쓰는 것은 계약에 어긋나지 않는다고 본다. 근거: 호출자 u3의 2초 안에 502까지 끝나야 하고, u1의 목표가 로컬 500ms 이하이지만 메모리 조회라 보통 수 ms이며 재시도가 지연 한 번을 흡수한다.
- [assumption] 구독 수 상한 32와 503 `SUBSCRIPTION_LIMIT`은 계약 C3에 없는 오류 응답이다. 데모 규모에서 도달하지 않는 값이며 응답 추가는 계약 변경 규칙상 안전하다고 본다. u4-web-ui는 이 코드를 일반 오류로 취급해도 된다.
- 열린 질문: 없음.
