## 웹훅 처리 경로

```
본문 읽기(8KB 한정) → 서명 검증 → JSON 해석·형식 검증 → paymentId 조회 → 이벤트 잠금 → 중복 조회
  → u2 결과 반영 호출 → Payment 잠금 → 이벤트·상태 기록 → 응답
```

- 중복 이벤트와 서명 거부는 u2를 부르지 않는 짧은 경로라 20ms 안에 끝난다(NFR1.2, NFR1.3).
- 이벤트 잠금은 같은 eventId에만 걸린다. 서로 다른 eventId는 병렬로 처리된다(NFR4.2).
- 웹훅은 이벤트 잠금 다음에 paymentId 기준 Payment 잠금도 얻고 그 잠금을 쥔 채 u2를 호출한다. 같은 Payment에 대한 서로 다른 eventId의 웹훅은 서로 순서대로 처리되고(그래서 Payment.status가 u2 판정을 따른다), 서로 다른 Payment의 웹훅은 서로 막지 않는다. 결제 요청 경로는 Payment 잠금을 u2 호출 중에는 쥐지 않는다(Payment는 u2 응답 뒤에 만든다).
- 잠금 획득 순서는 이벤트 잠금(웹훅) 또는 (세션, 멱등 키) 잠금(결제 요청) → Payment 잠금 → 저장소 맵(잎)이다. 역순 획득은 없다.

| 설계 | 방식 | 충족하는 요구사항 |
|---|---|---|
| 메모리 안 처리 | Payment, WebhookEvent, PgRequest는 맵에 둔다. 웹훅 처리의 외부 호출은 u2 결과 반영 한 번뿐이다. | NFR1.1 |
| 짧은 경로 우선 | 서명 검증과 형식 검증과 중복 조회를 u2 호출보다 앞에 두어 거부·중복이 u2 시간에 영향받지 않는다. | NFR1.2, NFR1.3 |
| 결제 요청 응답 먼저 | 결제 요청(C2)은 u2 예약 생성(성공 시 Payment 저장) 뒤 모의 PG에 요청을 등록만 하고 202를 돌려준다. 등록은 스케줄러에 작업을 넣는 연산이라 응답을 막지 않는다. | NFR1.4, NFR1.6 |
| u2 예약 생성 호출 마감 | 요청을 받은 시각부터 재는 전체 마감 1.5초. 같은 키의 잠금 대기와 u2 호출이 이 마감을 나눠 쓰며, 호출의 연결 제한과 읽기 제한은 남은 시간을 넘지 않게 합쳐 건다. 시도 1회, 재시도 없음. 호출자 u4의 제한 시간 2초 안에 502까지 끝난다. 이 값은 같은 유닛 기능 설계의 BR1.2·W1이 적은 "제한 시간 2초"를 대체한다. 계약 표의 2초보다 짧은 호출자 쪽 제한이라 계약에 어긋나지 않는다(호출하는 쪽이 더 짧은 제한을 쓸 수 있다). | NFR1.5, NFR5.4 |
| u2 결과 반영 호출 | 시도 하나의 제한 2초, 200ms 간격 최대 2회 재시도(계약 표 그대로). 최악 약 6.4초는 150ms 예산 밖이며 받아들인다(performance-requirements.md의 자원 제약). | NFR5.3 |
| 모의 PG 스케줄러와 발송 분리 | 지연은 스케줄러(스레드 1개)가 맡고 시각이 되면 발송 작업을 별도 발송 실행기(스레드 4개)에 넘기기만 한다. 웹훅 자기 호출의 제한 시간은 2초다. 호출이 느려도 스케줄러가 붙들리지 않아 다른 알림의 지연 오차가 늘지 않는다. 발송 실행기 큐가 가득 차 거부되면 스케줄러 스레드 안의 작업이 그 알림을 포기하고 로그를 남긴다. | NFR1.6, NFR4.5 |
| 지연 알림 수용 | 지연 알림 한 건은 스케줄러의 예약 작업 하나(메모리 객체)다. 수십 건은 문제없다. | NFR4.5 |

## 시험 방법

- 측정 구간: 요청 필터 진입부터 응답 쓰기까지(NFR1.1~NFR1.4, NFR1.5). u2는 정상 응답하는 가짜(지연 50ms 이하)로 대체한다(NFR1.1). NFR1.5는 응답 없는 가짜 u2로 502까지의 시간을 재고(1.7초 이하), 같은 키로 동시에 두 요청을 보내 첫 호출이 응답하지 않을 때 두 번째 요청도 요청을 받은 때부터 1.7초 안에 502를 받는지 확인한다.
- 반복: 처음 20회는 예열로 버리고 이어지는 100회의 최댓값을 목표와 비교한다. JVM 정지로 흔들리면 같은 시험을 한 번 다시 실행해 두 번 모두 넘으면 실패로 본다.
- NFR1.6: (a) 주입 시계로 DELAY 지연이 지정한 초 뒤에 발송되는지 확인하고, (b) 실제 스케줄러로 지연 2초 알림 20건을 예약해 모든 알림이 2초 ± 1초 안에 도착하는지 확인한다. APPROVE·FAIL은 100회 반복에서 202 응답 뒤 웹훅 호출 시작까지의 최댓값이 100ms 이하인지 확인한다.
- NFR4.5: 지연 5초 알림 50건을 예약하고 모두 5초 ± 1초 안에 발송되는지 확인한다. 알림을 받는 쪽은 시험용 수신 서버다.

## Assumptions & Open Questions

- [assumption] u2 예약 생성 호출의 마감 1.5초는 계약 C5의 제한 시간 2초보다 짧은 호출자 쪽 제한이다. 근거: u4의 결제 요청 제한 시간 2초 안에서 502가 사용자에게 닿아야 한다. 계약 문서는 이미 검토가 끝나 고치지 않는다.
- 열린 질문: 없음.
