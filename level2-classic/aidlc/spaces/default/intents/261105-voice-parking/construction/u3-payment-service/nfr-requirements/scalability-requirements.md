| ID | 요구사항 | 측정 방법 | 출처 |
|---|---|---|---|
| NFR4.1 | 서비스는 데모 규모의 동시 사용에서 성능 목표를 지켜야 한다. 동시 세션 10개가 각자 결제 요청과 웹훅 처리를 진행해도 NFR1.1(150ms)과 NFR1.4(500ms)를 지킨다. | 동시 10 세션 시험에서 두 목표 확인 | NFR1, NFR4 |
| NFR4.2 | 서로 다른 결제·서로 다른 eventId·서로 다른 멱등 키의 처리는 서로를 막지 않는다. 직렬화는 같은 eventId 안, 같은 (세션, 멱등 키) 안에서만 일어난다. | 동시 시험: 서로 다른 이벤트 N건 처리가 병렬로 진행됨 | NFR4, BR3.4 |
| NFR4.3 | 이 서비스는 한 개의 프로세스만 띄운다. 결제 기록, 처리한 이벤트, 예약된 모의 PG 알림이 프로세스 메모리에 있으므로 여러 개를 띄우는 것은 지원하지 않는다. 포트 8083을 고정해 두 번째 인스턴스는 기동에 실패한다. | 설계 확인 | NFR4, BR5.1 |
| NFR4.4 | 모의 PG 구성 요소와 웹훅 수신·Payment 로직은 패키지 경계를 나눈다. 모의 PG를 걷어내도 나머지가 빌드되고 시험된다. | 패키지 의존 방향 시험(Payment·웹훅 패키지가 모의 PG 패키지를 참조하지 않음) | NFR4, BR2.2, ADR-005 |
| NFR4.5 | 모의 PG의 예약된 알림 수는 결제 건수에 비례한다. 알림 스케줄러는 지연 알림(최대 600초) 수십 건을 감당한다. | 지연 알림 50건을 예약한 시험에서 모두 제때 발송됨 | NFR4, BR2.1 |

## 범위 밖

- 자동 확장, 부하 분산, 영속 저장소, 결제 기록 정리(만료 삭제)는 다루지 않는다. 별도 배포 환경이 없어(NFR8) 확장 환경이 존재하지 않는다.
