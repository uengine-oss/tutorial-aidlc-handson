| 설계 | 방식 | 충족하는 요구사항 |
|---|---|---|
| 이벤트 단위 직렬화로 멱등 | 웹훅은 이벤트 잠금 안에서 (1) 기록된 eventId를 조회해 있으면 DUPLICATE로 끝내고 (2) 없으면 u2를 호출하고 (3) 성공하면 WebhookEvent를 기록한다. 조회·호출·기록이 한 잠금 안이라 같은 eventId는 u2 호출이 한 번만 성공한다. 재시도는 같은 호출 안의 반복이고 성공 호출은 하나다. | NFR5.1 |
| 호출 성공 뒤 기록 전 예외 | u2 반영 성공 뒤 기록 전에 예외가 나면 이벤트는 기록되지 않아 다음에 같은 이벤트가 오면 u2를 다시 부른다. u2 결과 반영이 같은 eventId에 처음 낸 결과를 그대로 돌려주는 멱등 연산이므로(계약 C5) 재처리는 안전하다. | NFR5.1, NFR5.8 |
| u2 실패 시 미기록 | u2 반영 호출이 재시도 후에도 실패하거나 오류를 돌려주면(404·400·502 포함) 502 UPSTREAM_FAILED를 돌려주고 WebhookEvent도 Payment.status도 바꾸지 않는다. | NFR5.2 |
| 결과 반영 호출 | 시도 하나의 제한 2초, 200ms 간격 최대 2회 재시도(총 3회 시도). 같은 eventId라 재시도가 안전하다. | NFR5.3 |
| 예약 생성 호출 | 마감 1.5초, 시도 1회, 재시도 없음. 실패하면 502 UPSTREAM_FAILED이고 Payment를 만들지 않는다. 사용자가 같은 멱등 키로 다시 요청하면 u2의 멱등으로 이어 간다. | NFR5.4 |
| 같은 키 원자 처리 | 결제 요청은 (세션, 멱등 키) 잠금 안에서 u2 호출, Payment 조회 또는 생성, 모의 PG 요청 등록을 한다. u2가 201이면 Payment를 만들고 모의 PG에 등록한다. 200이면 같은 키의 Payment를 찾아 쓰고, 없으면 만들되 예약이 결제 대기이고 그 Payment에 PgRequest가 없을 때만 등록한다. PgRequest가 이미 있으면 다시 등록하지 않는다. 동시에 온 같은 키 요청은 이 잠금에서 순서대로 처리되어 Payment 1건, 모의 PG 요청 1회가 된다. u2 호출이 잠금 안에서 일어나므로 같은 키의 두 번째 요청은 첫 호출이 끝날 때까지 기다린다. 마감은 요청을 받은 시각부터 재는 한 값(1.5초)이며 잠금 대기와 호출이 나눠 쓴다: 잠금은 남은 시간만큼만 `tryLock`으로 기다리고, 얻은 뒤 남은 시간이 200ms 미만이면 호출하지 않고 502 UPSTREAM_FAILED로 끝낸다. 호출의 연결·읽기 제한은 남은 시간을 넘지 않게 합쳐 걸어, 어떤 경우에도 요청은 요청을 받은 때부터 1.5초 안에 응답한다(호출자 u4의 2초 안). 이 값은 BR1.2·W1의 "제한 시간 2초"를 대체한다. 잠금 객체 맵은 정리하지 않는다(결제 기록과 같은 취급, 범위 밖). | NFR5.5, NFR1.5 |
| Payment 단위 웹훅 직렬화 | 웹훅 처리는 이벤트 잠금을 얻은 뒤 paymentId 기준 Payment 잠금도 얻고, 그 잠금을 쥔 채 u2를 호출하고 상태를 기록한다(잠금 순서: 이벤트 잠금 → Payment 잠금). 같은 Payment에 서로 다른 eventId가 동시에 와도 한 건이 u2 판정과 기록을 끝낸 뒤 다른 건이 시작한다. 그래서 Payment.status는 u2가 먼저 판정한 쪽을 따른다(예: u2가 APPROVED를 APPLIED로 확정하면 Payment는 APPROVED이고, 뒤에 온 FAILED는 u2가 REJECTED를 돌려줘도 Payment를 바꾸지 않는다). 모의 PG는 결제당 이벤트를 하나만 보내므로 같은 Payment의 동시 웹훅은 위조·시험 상황에 한정되고, 서로 다른 Payment의 웹훅은 서로를 막지 않는다. | NFR5.6 |
| 종료된 Payment | Payment가 이미 종료 상태(APPROVED, FAILED, IGNORED)이면 u2에는 전달하고(예약 서비스가 판정한다) 결과가 REJECTED이면 WebhookEvent만 IGNORED로 기록하며 Payment.status는 바꾸지 않는다. 결과가 APPLIED이어도 이미 종료 상태인 Payment는 바꾸지 않는다. | NFR5.6 |
| 모의 PG 자기 호출 실패 | 발송 작업이 연결 거부·오류 응답을 받으면 결제 ID와 원인(`PG_CALLBACK_FAILED`)을 오류 로그에 남기고 다시 보내지 않는다. 호출의 제한 시간은 2초다. 시간 초과는 서버 처리가 이어져 적용됐을 수 있으므로 원인을 `PG_CALLBACK_NO_RESPONSE`("응답 미확인")로 구분해 남긴다. 발송 실행기 큐가 가득 차 거부되는 경우의 처리 주체는 스케줄러 스레드 안의 작업이며, 그 알림을 포기하고 `PG_CALLBACK_DROPPED`를 남긴다. | NFR5.7 |
| 전역 예외 처리 | 처리하지 못한 예외는 500 INTERNAL_ERROR와 공통 오류 형식으로 돌려주고 로그에 남긴다. 상태 변경은 잠금 안에서 한 번에 저장하는 값 교체로 하고, 중간에 예외가 나면 이전 값이 남는다. | NFR5.8 |
| 재시작 | 재시작하면 모든 메모리 상태가 사라진다. 시작할 때 기록은 비어 있고 예약된 알림을 복구하지 않는다. 사라진 결제에 대한 웹훅은 404 UNKNOWN_PAYMENT다. | NFR5.9 |
| 가용성 목표 없음 | 가용성 목표는 정하지 않는다. 서비스가 죽으면 실행 스크립트로 다시 띄운다. 회로 차단기는 두지 않는다(호출처가 u2 하나이고 마감이 짧다). | NFR5.10 |
| 시계·스케줄러 주입 | 모의 PG는 `Clock`과 스케줄러 인터페이스를 주입받아 시험에서 지연을 앞으로 돌린다. 실제 스케줄러 경로는 짧은 지연으로 한 번 확인한다. | NFR5.11 |
| 품질 게이트 | 병합 전에 `mvn verify`(시험과 JaCoCo 80% 검사 포함)를 실행하는 것을 병합 전 검증으로 본다. 이 실행은 u5-local-run의 검증 스크립트로 제공한다. | NFR7.1 |

## 장애 시 동작

| 장애 | 동작 |
|---|---|
| u2 중단·지연 (결제 요청) | 1.5초 안에 502. Payment 없음. 같은 키로 다시 요청 가능 |
| u2 중단·지연 (웹훅) | 최대 약 6.4초 뒤 502, 이벤트 미기록. 모의 PG는 재전송하지 않아 승인이 유실될 수 있고 예약은 u2가 자동 취소한다 |
| 모의 PG 자기 호출 실패 | 오류 로그. 재전송 없음. 시간 초과(`PG_CALLBACK_NO_RESPONSE`)는 서버 처리가 이어져 적용됐을 수 있고 유실이 아닐 수 있다 |
| 발송 실행기 큐 가득 | 해당 알림을 포기하고 오류 로그(`PG_CALLBACK_DROPPED`). 데모 규모에서는 일어나지 않는다 |
| 재시작 | 결제 기록과 예약된 알림 소실. 예약은 u2가 자동 취소한다 |

## Assumptions & Open Questions

- [assumption] 같은 키 요청이 서로 기다리는 것을 받아들인다. 대기와 호출을 합친 마감이 요청을 받은 때부터 1.5초이므로 기다리다 마감을 넘기면 502이며 같은 키로 다시 요청하면 이어 간다. 근거: 같은 키 동시 요청은 더블 클릭 같은 드문 경우이고 서로 다른 키는 막지 않는다. 대기 요청이 서블릿 스레드를 점유하는 시간도 1.5초를 넘지 않는다.
- [assumption] 발송 실행기 큐 상한 64를 넘는 알림은 포기한다. 근거: 데모 규모에서 도달하지 않는 값이다.
- 열린 질문: 없음.
